# 原版运行开销

性能调整保持原版 30 FPS、模拟步进、集合遍历顺序、寻路规则和存档格式。构建时独立执行优化与逆向审计，不把性能改动混入汉化绑定。

## 枚举器释放的临时分配

原版旧编译器在部分 `foreach` 的 `finally` 中，将集合的值类型枚举器装箱，再调用 `IDisposable.Dispose()`。它不是集合内容的快照，但每次执行都会产生一个只用于释放的短命对象。这个模式出现在单位更新、能量分配和 CRPL 寻路等路径。当前 Mac Steam 2.12 原版程序集识别到 406 处。

`src/performance/EnumeratorDisposePatch.cs` 只处理已知 BCL 集合的枚举器：List、HashSet、Dictionary（含 Keys/Values）、Queue 和 Stack。构建器核对真实类型为实现 IDisposable 的结构体，然后把装箱替换为“保存到新增局部变量、取得副本地址、constrained 调用原 Dispose”。它不会省略释放，也不会直接修改原来的枚举器局部变量，因此保留原先对副本执行 Dispose 的语义。所有原循环与异常处理边界保持不变；不改 ManagerPool 返回的快照或 A* 的开放集合与平局选择。

优化没有新增运行时组件、公共接口、缓存或依赖，仍作用于 Assembly-CSharp.dll。它不属于包外渲染更新：安装包含此项的完整候选会更新 app 内程序集，应按现有安装器处理签名。只改源码不影响已安装游戏。

构建会执行行为契约和单独的逆向审计：检查泛型、空集合、原枚举器继续使用、嵌套循环、提前返回、异常、遍历时集合修改，以及未经支持的自定义枚举器。审计精确移除每个新增指令和局部变量后，再比较整份程序集的字段、方法、原指令与异常处理范围。不能完整还原时构建失败。

验证入口：

```sh
python3 tools/test.py --config /path/to/build-config.json --suite EnumeratorDisposeContracts
```

该测试只需 Mono 和 Cecil，不需要游戏或字体文件。分配量检查在宿主提供 `GC.GetAllocatedBytesForCurrentThread` 时运行；它证明此模式的临时分配被移除，不代表整局游戏的 CPU、帧率或输入延迟收益。实机收益还取决于地图、单位数量、脚本负载及游戏内 Mono 的 GC 行为。若新的受支持原版不再使用此模式，或类型/结构审计不通过，应停止应用并重新检查，而非放松校验。

## 多脚本显示上下文

汉化显示需要核对 CRPL 原文哈希，并为数字输出找到原始命令序号。原实现分别只记住上一份脚本和上一组命令，多个脚本交替显示时会重复计算 SHA-256、分配序号数组并反射扫描全部命令。

`ScriptContextCache` 只缓存这两类纯派生结果。原版 `ScriptManager.GetScript` 返回字典中已有的不可变字符串；编译缓存命中时复用命令列表，重新编译时创建新列表。因此哈希以源字符串身份为键，序号以命令列表身份、长度与源哈希共同为键，不能仅凭脚本名复用。相同名称的不同脚本、原文替换、命令替换及源码漂移仍经过原来的绑定检查。原有 16,384 条命令限制不变。

哈希缓存最多 16 项，序号缓存最多 8 项，序号数组总计不超过 32,768 个整数（128 KiB，另有少量索引开销）。源字符串和命令列表都使用弱引用；场景切换或运行时对象销毁时清空。超过容量时淘汰最久未用项，计算异常不会发布不完整缓存。这是以少量有界驻留空间换取更少的反复扫描与临时数组，并不承诺常驻内存必然下降。

现有 27 条数字输出绑定涉及 Message.crpl、Train_Scores.crpl 和 timer.crpl。收益取决于实际地图是否让多个相关脚本交替输出；单脚本原本已能命中缓存，不应据此推断整局帧率提升。

两个不依赖游戏文件的契约覆盖缓存容量、弱生命周期、重编译失效、异常恢复，以及真正的 CaptureCrpl/ForGuiMessage 翻译与场景回调：

```sh
python3 tools/test.py --standalone --suite ScriptContextCacheContracts --suite ScriptContextRuntimeContracts
```

它们也进入默认源码检查。原生 Mac 的实现位于外置 CW3ExternalRuntime.dll，配套 fonts.json 哈希需要一起更新；这项实现变化不会改变稳定薄桥或游戏程序集。

## 原版对象池快照

原版每次更新能量包、雾和特效时，都会分配一份数组，再按 HashSet 的现有顺序复制活跃对象。更新过程中对象可以回池、加入或复用，不能直接改成遍历集合，也不能把公开返回的数组变成共享数组。

此优化只改 EffectsUpdate、PacketsUpdate 和 MistUpdate 中的五个调用。每个池按需保留一份容量数组，循环使用获取时捕获的数量，并在独立 finally 中清除已用引用、归还给获取时的同一个池。空池不分配；同池重入或超过 16,384 项时回退原来的独立数组。三个能量包池仍在各自循环开始时才捕获，不提前合并快照。公开 GetActiveManagers、存档以及关闭特效的调用保持原样。

数组容量按二次幂增长，每池最多 16,384 项。在 64 位进程中最多约 128 KiB 引用槽位；五个常用池合计预算约 640 KiB，加少量数组头和字段。这是明确的缓存上限，不是实测最优值。归还只清有效前缀，不因历史峰值反复清整份大数组。它减少稳态临时数组分配，不省掉 HashSet.CopyTo，也不据此宣称整局 CPU、帧率或常驻内存下降。

构建会锁定三个原更新方法及两个快照生产方法的完整规范化 IL、局部与控制流，拒绝未知布局和重复补丁。验证器检查完整变换，逐项撤销新增调用、局部、finally、池字段和方法，再比较整程序集。契约覆盖增删与同引用复用、重入、捕获池被替换、异常清理、容量边界、公开数组所有权，以及注入复制故障后的引用释放：

```sh
python3 tools/test.py --config /path/to/build-config.json --suite ManagerSnapshotContracts
```

这项修改位于游戏程序集，原生 Mac 安装需要更新 .app 并重签；与仅更新包外显示实现的部署范围不同。
